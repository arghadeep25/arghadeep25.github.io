What is SLAM?

Drop a robot in a room it has never seen. To draw a map it must know where it is. To know where it is, it needs a map. SLAM means Simultaneous Localisation And Mapping: solve both together, because neither can wait for the other. It is a chicken-and-egg problem.

Why not use GPS? Indoors, underground and between tall buildings there is none. The robot only has its own senses: wheels that count turns, and a camera or laser that sees what is around.

Why this formula

We never see the true path or the true map. We only get noisy evidence. Probability lets us ask the one question that makes sense: which path and map are the most believable, given everything the robot saw and did?

Why it matters

It turns "where am I, and what is around me?" into a single, well-posed question. Everything else in this post is a way of answering it.

Graph SLAM in one picture

Graph SLAM turns that chicken-and-egg problem into a drawing. Every place the robot stood becomes a node. Every fact it measured becomes an edge, a string between two nodes. Then one question is left: slide the nodes until all the strings are as relaxed as they can be.

Node
a pose x = (x, y, θ), or a landmark position m = (x, y)
Odometry edge
the move u between two poses: how far, how much it turned
Landmark edge
an observation z: range r and bearing φ from a pose to a landmark
Loop closure edge
a pose that matches an old pose, so the lap is shut

Frontend and backend

A SLAM system has two halves. Think of a kitchen. The frontend is the prep cook: fast, always chopping, sometimes sloppy. It reads sensors, finds features, guesses which ones match, and builds the graph. The backend is the chef who tastes everything: slow, careful, and fixing the whole dish at once. It takes the graph and finds the pins that make the strings happiest.

Keeping them apart pays off. You can swap a camera for a lidar and only the frontend changes. You can swap in a faster solver and only the backend changes. The graph in the middle is the handshake.

Walking with your eyes closed

The robot counts its steps. Every count is a tiny bit wrong, and the mistakes add up.

Why this formula

To solve for the robot's path we need something small to solve for. On a flat floor, three numbers are enough to place a rigid robot: where it is (x, y) and which way it faces (θ).

Why it matters

These are the unknowns. A trip of N pins is 3N numbers to find. The heading matters most: a small turn error at pin 5 swings every later pin far off its place.

Every kind of fact becomes the same thing: an error that is zero when the pins agree. Odometry, landmarks and loop closures differ only in h and z, so one solver can handle all of them.

This is how landmarks are tied to the pins: a prediction we can compare with a reading. Subtracting θ makes the bearing relative to the robot's nose, which is why a heading error corrupts every landmark seen from that pin.

Why this formula

A plain sum would treat every string alike, but a precise sensor deserves a louder voice. Multiplying the error by Ω weights it by trust. Squaring means a stretch in either direction costs the same, and big stretches cost much more. The weight is 1/σ²: a sensor twice as precise counts four times as much.

Why it matters

Metres and radians cannot be added raw. Ω puts them on one scale. It also comes straight from the sensor's spec sheet, so a wrong σ gives a map that is either blurry (too little trust) or overconfident (too much).

Loop closure: "I have been here!"

Look at the strings before the robot returns: all relaxed, and yet the map is wrong. Then the robot recognises the start. One new string joins the last pin to the first, and that string is very stretched. Every pin on the way gets pulled a little, and the lap snaps shut.

From "likely" to "cheap"

Why add up squared errors? Because sensor noise is bell-shaped: small errors are common, big errors are rare. Ask for the most likely map and, with a little algebra, you are asking for the map with the lowest total price. Flip the bell upside down with a logarithm and it becomes the bowl we roll down.

Why this formula

Sensor noise is bell-shaped, and a bell has the form exp(−½ e² Ω). The whole trip's likelihood is a product of many bells. Taking −log turns that product into a plain sum of squares.

Why it matters

This is why we minimise squared errors. It is not a habit. It is the most likely map when noise is bell-shaped. Sums are also easy to optimise, while a product of thousands of tiny numbers just underflows to zero.

Why this formula

Each string is an independent piece of evidence, so their likelihoods multiply and their prices add. The best map is the one where that total is lowest, which is what argmin picks.

Why it matters

All of SLAM becomes one number to push down. And because every pin shares that number, one new loop-closure string changes the price everywhere, which is why it corrects the whole lap and not only the last few pins.

Why this formula

F bends with the turning angles, so we cannot jump to the answer. Near the current guess we can straighten it out: J says how each error changes when a pin moves. That gives an exact bowl, solved by H Δx = −b. H adds up how stiff each string is, b adds up how hard each one pulls. Step, then repeat. This is Gauss-Newton.

Why it matters

A few cheap linear solves beat blind guessing. H is sparse, because a pin only touches its neighbours, so thousands of pins solve in milliseconds. It needs a decent starting guess, which is why the frontend's odometry matters.

How sure is each pin?

A good map says more than where things are. It also says how sure it is. Each pin wears a cloud: the place it might really be. The cloud grows with every step of counting, and shrinks when a loop closure ties the ends together.

Why this formula

H tells how stiff the graph is around each pin. A stiff pin has little room to move. Its inverse flips that into how much room each pin still has.

Why it matters

It gives an honest "how sure" for every pin. The doubt grows with distance from the anchor and shrinks after a loop closure. Planners and loop-closure checks use it to know when not to trust a pin.

When a string lies

Sometimes the robot is fooled. Two corridors look the same, so it ties a string between two places that are far apart. One liar can crush the whole map. The fix: a string that is stretched far too much is probably lying, so listen to it less and less.

The whole recipe

That is all of Graph SLAM. Go round this list again for every new step.

  1. Drop a pinfor every step the robot takes.
  2. Tie a stringfrom the last pin to the new one.
  3. Say how sureeach string is. A sure string is stiff.
  4. Spot an old placeand tie a string back to its pin.
  5. Add up the pricesof all the stretched strings.
  6. Roll downhilluntil the price stops falling.
  7. Doubt liarsand keep a cloud of doubt on every pin.
